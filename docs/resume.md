# 项目经历与面试准备

项目名可以写为：**设备遥测采集与监控网关（主机模拟）**。
阅读、复现测试并能解释实现后，按实际工作情况改写以下内容：

- 基于 C++17、cpp-httplib 和 SQLite 实现本地遥测网关，接入 C99 帧解析组件，
  按输入来源隔离拆包状态，完成 CRC 校验、半帧超时、字段校验与历史查询。
- 采用有界生产者/消费者队列隔离接收与存储，设计队列拥塞、解析错误和存储失败统计；
  配套 Python 多设备模拟器、故障注入、黑盒集成测试及网页监控与 CSV 导出。

不要把调用 cpp-httplib 描述为自己实现 HTTP、epoll、Reactor 或线程池内核。
不要把 SQLite 的 WAL 能力写成自己设计了日志恢复算法。
性能指标只能引用自己在明确环境和参数下复现的测量，不套用上游数据。

## 应能解释的问题

1. HTTP 有消息边界，为什么仍然需要拆包解析？当前传输与真实 UART 有何区别？
2. 为什么不同来源必须拥有不同解析状态？相同来源并发分块为什么会破坏顺序？
3. 为什么回调里要复制字段，而不能把 payload 指针排队？
4. 为什么 HTTP 202 不等于持久化成功？队列满时客户端能否整块重发？
5. 为什么用单调时钟做超时，却用系统时钟写入数据库？
6. worker 出队后再写入，统计中可能出现什么暂时不相等？
7. SQLite 写入慢时，哪些操作会互相阻塞？如何通过批量事务或独立读连接改进？
8. CRC 校验通过但 payload schema 不符时应当如何计数？
9. 强制杀进程后，哪些数据可能丢失？如何验证已提交记录仍可读取？
10. 为何没有开发板时不能声称已完成 UART/DMA 性能验证？

## 后续可独立完成的改进

先选择一个需求、设计验收测试，再修改实现，例如：

- 加入序列号与会话标识，实现可解释的去重与设备重启语义。
- 引入批量事务，比较延迟、吞吐和突然终止时的数据损失窗口。
- 增加数据保留策略，限制数据库磁盘增长。
- 新增真实 UART 输入适配器，再接入开发板验证收发与故障恢复。

当前项目是既有协议组件的系统级扩展。简历可将两者合成一个完整项目，
避免把高度重叠的工作拆成多个项目重复占篇幅。
